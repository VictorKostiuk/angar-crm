# Angar CRM — Bike Workshop CRM: Build Plan

**Stack (already in the repo):** Rails 8.1.3, PostgreSQL 17, Propshaft, Tailwind CSS **v4**, Hotwire (Turbo + Stimulus), importmap, Solid Queue/Cache/Cable.
**Language:** UI is Ukrainian, code/DB/docs are English (glossary in §3).
**Source of truth for screens:** `docs/mockups/` (17 images, index in §4).

> **How to edit this plan:** every decision has an ID (`D1`, `D2`, …) and every phase a number (`P1.3`).
> Change the value in the table in §1, or write `❌ no, do X instead` next to it — that is enough for me to pick it up next session.
> Nothing below §1 is implemented yet; no code has been written.

## 2. What this app is

A workshop-floor tool for a bike repair shop. The daily loop is:

```
client walks in → intake (client + bike + problem) → order created (Нове)
   → mechanic works, adds works & parts to the order → status changes
   → total is agreed with the client → payment → bike handed over → order closed
   → closed orders feed reports & mechanic payroll
```

Everything else in the app exists to serve that loop: catalogs make line entry fast, the board shows what is on the floor right now, reports turn closed orders into money numbers.

## 5. Data model

Money = `decimal(12,2)`. All tables have `created_at/updated_at`. `→` = foreign key.

### v1 tables

**users** — staff
`name`, `email_address` (unique), `password_digest`, `role` enum(mechanic/admin/owner), `payroll_percent` decimal(5,2) default 0, `phone`, `active` bool default true

**sessions** — from the Rails 8 auth generator
`→ user`, `ip_address`, `user_agent`

**clients**
`name`\*, `phone`\* (normalized, unique), `email`, `city`, `notes` text, `bikes_count`, `orders_count`
_indexes:_ `phone` unique, `name` (trigram search later)

**bikes**
`→ client`\*, `name`\*, `brand`, `model`, `color`, `size`, `notes`, `active`

**categories**
`kind` enum(service/part)\*, `name`\*, `position`, `active`
_unique:_ `[kind, name]` — e.g. Трансмісія, Гальма, Колеса / Ланцюги, Камери, Покришки

**services** — Роботи catalog
`→ category`, `name`\*, `base_price`\*, `active`, `position`

**parts** — Деталі / матеріали catalog
`→ category`, `name`\*, `base_price`\* (selling price), `sku`, `active`, `position`,
`→ supplier` (nullable, P7), `purchase_price` (nullable, cost — independent of `base_price`, no markup calc between them, P7), `stock_quantity` default 0 (derived, sum of `stock_movements.quantity`, P7), `min_stock_level` default 0 (P7)

**orders**
`number`\* (unique, from sequence), `→ client`\*, `→ bike`\*, `→ mechanic` (users, nullable), `→ accepted_by` (users)\*,
`status` enum\*, `problem` text, `comment` text,
`accepted_at`\*, `expected_ready_on` date, `closed_at`, `cancelled_at`, `cancel_reason`,
`payment_status` enum(unpaid/paid), `paid_at`, `payment_method` enum(cash/card/transfer), `receipt_number`,
`works_total`, `parts_total`, `discount`, `total` (all default 0)
_indexes:_ `status`, `[status, accepted_at]`, `mechanic_id`, `client_id`, `payment_status`, `closed_at`

**order_works** — labour lines
`→ order`\*, `→ service` (nullable = custom line), `→ mechanic` (nullable, defaults to `order.mechanic`), `name`\* (snapshot), `quantity` **decimal(8,2)** default 1 (half-hours happen), `price`\* (snapshot), `total`\*, `position`

**order_parts** — material lines
`→ order`\*, `→ part` (nullable = custom line), `name`\*, `quantity` **integer** default 1, `price`\*, `total`\*, `position`

**order_status_changes** — timeline / audit
`→ order`\*, `→ user`\*, `from_status`, `to_status`\*, `comment`, `created_at`

**settings** — single row: shop name, address, phone, default payroll %, currency

### Rules baked into the schema

- Line items **snapshot** `name` and `price` — editing a catalog price never rewrites past orders (D19 keeps the catalog row alive too).
- `orders.works_total / parts_total / total` are **stored and recalculated** on every line change (`Orders::RecalculateTotals`), so lists and reports never sum children.
  `total = works_total + parts_total − discount`.
- `accepted_by_id ≠ mechanic_id` is normal (mockup 04: прийняв Женя, механік Андрій).

### P7 tables (Suppliers & Stock — concrete, see D25–D27)

**suppliers**
`name`\*, `phone`, `email`, `notes` text, `active` bool default true

**stock_movements** — immutable audit ledger, single writer of `parts.stock_quantity` (same discipline as order totals: never trust a counter, sum the ledger)
`→ part`\*, `→ user` (nullable — nil for system-generated consumption), `→ order` (nullable — set only when `kind: consumption`), `kind` enum(receipt/write_off/consumption/adjustment)\*, `quantity`\* (signed integer: positive = stock increased, negative = decreased; `kind` is metadata for the audit trail, the sign is what's authoritative), `note`
_no update/destroy — corrections are a new `adjustment` movement, not an edit to history (same pattern as `order_status_changes`)_

`Parts::RecalculateStock` recomputes `parts.stock_quantity = SUM(stock_movements.quantity)` on every `stock_movements` create — mirrors `Orders::RecalculateTotals` exactly, so a movement inserted by any future code path self-heals the counter instead of silently drifting it.

`Orders::Close` gets one addition: for every `order_parts` line with `part_id` present (custom/non-catalog lines have nothing to decrement), create a `kind: consumption` movement for `-quantity`, attributed to the order. Never blocks the close (D26) — stock can go negative.

### P8 tables (Фінанси — concrete, see D28–D31)

**expenses**
`category`\* (string, free text — D28), `amount`\*, `description`, `date`\* (defaults to today, editable — the day the money went out, independent of `created_at`), `→ user` (who recorded it), `→ stock_movement` (nullable, **unique** — set only on auto-created rows, see below)
Unlike `stock_movements`/`order_status_changes`, expenses are a normal editable/deletable record (admin+owner), not an immutable ledger — typos in a manually-entered amount need fixing directly, and there's no "history of an expense changing" to protect.

`Finances::LogExpenseFromConsumption` runs from `StockMovement#after_create`, alongside the existing `Parts::RecalculateStock` call: when `kind == "consumption"` and `part.purchase_price.present?`, creates one `expenses` row (`amount: purchase_price * quantity.abs`, `category:` a fixed default string, `stock_movement:` self, `date: Date.current`, `user: nil` — consumption movements are system-generated). Skipped silently when `purchase_price` is nil — no cost data, nothing to book. The view tags auto-created rows ("витрачено на замовлення") so a human entering the same cost by hand can see it's already covered. **Revised from the original receipt-triggered design (D28)** — cost now books when the part is actually used, matching when its revenue books too.

**payroll_payouts**
`→ user` (mechanic being paid, role must be mechanic), `amount`\*, `period_month`\* (date, always the 1st of a month — D29), `note`, `→ user` (`recorded_by`, who entered it)
Owner-only to view/create (§7). No update/destroy — a correction is a new payout row (same "ledger, not edit" discipline as `stock_movements`), since this represents money that actually left the till.

Outstanding balance (owner-only, shown on the mechanic card) = `Reports::MechanicStats` row's payout for the **current calendar month** − `Σ payroll_payouts.amount` where `user:` that mechanic and `period_month:` the 1st of the current month — shown **only** when the Reports period filter is exactly "Цей місяць" (D29). Any other period shows the payout log with no arithmetic.

**Reports::ClosedRevenue** (`app/services/reports/`, not a table) — `call(range:)` → `{ works_total:, parts_total:, order_count: }` for closed orders in `range`, shop-wide, no mechanic filter. Introduced so Фінанси's P&L revenue line and the Звіти KPI tiles (status = closed, no mechanic selected — their default view) both read from the same computation instead of Фінанси re-deriving it from `MechanicStats` rows, which are keyed by mechanic and would silently drop an order whose `mechanic_id` points at a non-mechanic user (D30).

**P&L (P8.3, no new table)** — for the Reports-style period picker: Дохід = `ClosedRevenue`, Витрати = `Σ expenses.amount where date in range`, Прибуток до виплат = Дохід − Витрати (**admin sees up to here**). Owner additionally sees Виплати = `Σ payroll_payouts.amount where period_month in range` and Чистий прибуток = Прибуток до виплат − Виплати (D31).

`attachments` (Active Storage on orders) stays in P9 — unrelated to Фінанси, kept here only as a reminder it hasn't moved.

## 6. Order lifecycle (business rules)

```
                     ┌──────────────────────────────────────────┐
Нове ──► Очікує погодження ──► В роботі ──► Очікує запчастини ──┘
                                   │  ▲          │
                                   ▼  └──────────┘
                            Очікує видачі
                                   │  (payment + handover)
                                   ▼
                               Закрито            Скасовано (from any open status)
```

| Status | UI label | Badge |
|---|---|---|
| `intake` | Нове | gray |
| `waiting_approval` | Очікує погодження | amber |
| `in_progress` | В роботі | blue |
| `waiting_parts` | Очікує запчастини | violet |
| `waiting_pickup` | Очікує видачі | teal |
| `closed` | Закрито | green |
| `cancelled` | Скасовано | red |

Payment badge: Оплачено (green) / Не оплачено (amber).

**Rules — these are acceptance criteria, taken from the mockups:**

1. `closed` is **not** selectable in the status modal — only via "Закрити замовлення" (mockup 07 says so explicitly).
2. Closing requires: works entered, parts entered, total verified, **paid**, bike handed over (checklist, mockup 09).
3. A closed order **leaves the Майстерня board** and appears in history + reports (mockup 09).
4. Every status change may carry a comment (≤200 chars) and is written to `order_status_changes` — the order card shows this timeline.
5. Payment records method (готівка / картка / переказ) + optional Checkbox receipt number and sets `paid_at`.
6. Cancelling requires a reason; a cancelled order is never counted in revenue or payroll.
7. Payroll base = Σ `order_works.total` (grouped by `order_works.mechanic_id`) of **closed** orders in the period — **works only, D33**. Parts are still totalled per mechanic (by order ownership) and shown as context on the mechanic card, but they are **not** in the earning base. Payout = base × `payroll_percent`, rounded to whole hryvnia so it is payable exactly.
   `order.mechanic_id` is therefore **required to close an order** (part of the P4.5 checklist), and every work line inherits it unless overridden — so a closed order can never contain work that belongs to nobody. Without this rule, such work would count as revenue but silently disappear from the payroll table.
   The inheritance happens **once, at line-creation time** (`order_works.mechanic_id = order.mechanic_id` if the order already has one) — it is not a live fallback. If a work line was added before the order had a mechanic assigned, its `mechanic_id` stays `NULL` even after one is set later. So **P4.5's close checklist must backfill**: any `NULL`-mechanic work line on the order gets `order.mechanic_id` at close time (or the close is refused if the order itself has no mechanic). Money math (`order_works.total`, `decimal(8,2)` quantity × price) is rounded to 2dp **on write**, and every total above it (`works_total`, `parts_total`, `total`) is a sum of already-rounded line totals, never a re-multiplication — otherwise fractional quantities (e.g. 1.5h) drift the payroll base by a kopeck from what the UI displays.
8. Intake must be able to create the client **and** the bike inline — "Клієнта не знайдено. Створіть нового" (mockup 03). This is the make-or-break screen: it has to work with one hand while holding a bike.

## 8. Technical conventions

- **Rails-native, boring:** fat models with slim service objects for the 4 non-trivial operations — `Orders::Create` (intake), `Orders::RecalculateTotals`, `Orders::ChangeStatus`, `Orders::Close`. Everything else is plain CRUD controllers.
- **Hotwire, no SPA:** modals = one `<dialog>` + a `#modal` Turbo Frame; line items append via Turbo Streams; catalog search in modals = debounced Stimulus controller hitting a Turbo Frame. Full page reloads stay rare.
- **Tailwind v4 (CSS-first):** design tokens live in `@theme { … }` inside `app/assets/tailwind/application.css`. **There is no `tailwind.config.js`** in v4 — don't create one. Shared UI (badge, card, table, button, modal) = Rails partials + helpers, not `@apply` soup.
- **i18n:** every user-facing string in `config/locales/uk.yml` from the first commit; `rails-i18n` gem for dates/pluralization; helpers `money(amount)` → `1 920 грн`, `order_number(order)` → `#024`.
- **Testing:** Minitest + fixtures. Unit tests are mandatory for totals math, status transitions and payroll. One system test walks intake → works → parts → payment → close.
- **Seeds:** realistic Ukrainian data from the mockups (12 works, 8 parts, categories, 3 mechanics, ~10 clients/bikes/orders) so every screen has content while building. Seeded orders go through the **same service objects as the UI** (`Orders::Create`, line item creation, `RecalculateTotals`, `ChangeStatus`, `Close`) — never `create!` with hand-written totals, or seeded orders end up with `total = 0` while the UI shows the right sum, and P6 report numbers stop adding up.
- **Quality gates:** `rubocop-rails-omakase`, `brakeman`, `bundler-audit` (already in the Gemfile).
